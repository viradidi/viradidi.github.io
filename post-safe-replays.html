Making incremental loads safe to replay

7 November 2026·9 min read·Updated 22 November 2026
  • data-engineering
  • incremental-loading
  • idempotency
  • watermarks
  • delta-lake

An incremental load is not reliable because its first run completed. It is reliable when the same interval can be submitted again after an uncertain failure without losing records, duplicating business state or moving progress backwards.

That means designing for retries from the beginning. The control table, source cursor, target write and orchestration sequence form one correctness protocol. Across NovaCart, HealthGrid and Uber Eats, I use the same principles but adapt the exact cursor and replay contract to the source type.

Start with the failure boundary

Imagine a run extracts 10,000 rows, writes them to Bronze, and then the notebook or orchestrator loses its connection before it records success. The caller cannot tell whether the data write committed. On retry, it has two choices:

  • Move the checkpoint forward anyway and risk skipping rows if the write did not commit.
  • Read the interval again and rely on the target write to absorb a duplicate attempt safely.

The second option is usually the safer design. It deliberately allows at-least-once execution while making the target effect idempotent for the same source version. The system does not need every activity to run exactly once; it needs repeated execution to converge to the same correct state.

A useful distinction

“Exactly once” is often used too broadly. A pipeline that spans an API or database, object storage, Spark, Delta and a separate control table rarely has one atomic transaction across all of them. Describe the actual guarantee: for example, repeated delivery of the same key/version does not create a second Bronze version, and the checkpoint moves only after the durable write is confirmed.

Define a deterministic extraction cursor

A timestamp alone may not uniquely identify a position in a source table. Several rows can share one updated_at value, especially when a batch update changes many records in the same transaction. A cursor that stores only the timestamp can split a group at the boundary or reread every tied row indefinitely.

NovaCart stores a composite cursor for each source table: the last successfully processed timestamp and the primary key at that timestamp. Its incremental predicate is lexicographic:

def select_incremental_source_rows(
    source_df,
    primary_key_column,
    timestamp_column,
    last_successful_ts,
    last_successful_pk,
):
    if last_successful_ts is None:
        return source_df

    if last_successful_pk is None:
        return source_df.filter(
            F.col(timestamp_column) > F.lit(last_successful_ts)
        )

    return source_df.filter(
        (F.col(timestamp_column) > F.lit(last_successful_ts))
        | (
            (F.col(timestamp_column) == F.lit(last_successful_ts))
            & (F.col(primary_key_column).cast("long") > F.lit(int(last_successful_pk)))
        )
    )

In plain language, load rows with a timestamp after the stored timestamp, plus rows tied at the stored timestamp whose primary key is greater than the last processed key. This makes the cursor a stable position rather than a time-only cutoff.

The composite comparison has assumptions. The primary key must be non-null and sortable with a consistent order; NovaCart uses a numeric key cast to long. The timestamp must be maintained reliably by the source. The code normalizes timestamps to millisecond precision before comparison so the source value and stored checkpoint are compared at the same precision. It scans for null keys or timestamps and fails rather than letting SQL null semantics silently exclude a row.

The cursor also needs a documented initial-load rule. With no prior timestamp, NovaCart reads the initial source set. Once a timestamp is stored but no key exists, the helper uses a timestamp-only lower boundary. The control state must always be written consistently so a partially initialized cursor cannot become an ambiguous restart point.

Make the write idempotent

Reading the same range twice is not a problem if the target can recognize the same source version. In NovaCart, the Bronze Delta write merges on the configured primary key and source timestamp. That lets the table preserve distinct source versions while avoiding a second copy of the same key/timestamp version after a partial failure.

merge_condition = (
    f"target.{pk_col} <=> source.{pk_col} AND "
    f"target.{ts_col} <=> source.{ts_col}"
)

(
    target_delta.alias("target")
    .merge(rows_to_load.alias("source"), merge_condition)
    .whenNotMatchedInsertAll()
    .execute()
)

This is an abbreviated illustration of the match condition and insert path from the Bronze notebook; the full project code also manages the configured control record, audit fields and run ID. The target key is not merely the business primary key: it is the pair (primary_key, source_timestamp), because Bronze preserves separate observed versions of a record.

There is a useful limit to call out in this exact implementation: the Bronze MERGE inserts when the key/version pair is not present, but a matched pair is left as-is. That makes an identical replay idempotent; it does not independently prove that a second payload carrying the same key and timestamp is identical. If the source can mutate content without advancing its timestamp, add an explicit equal-version payload comparison and fail or reconcile on a mismatch. HealthGrid’s current-state Silver merge implements that stricter equal-version conflict check.

That is different from a current-state Silver table. A history-oriented Bronze table may intentionally contain multiple versions for one business key. A current-state Silver merge generally matches by business key and uses the source version as a condition for whether the target should be updated. The grain of the table determines the correct merge predicate.

Advance progress after the durable write

NovaCart's Bronze sequence is explicit: read the stored cursor, validate the source, select new rows, attach ingestion metadata, write the batch through Delta MERGE, and only then update the control table with the new successful timestamp, primary key, run ID and row count.

The failure cases become easier to reason about:

Failure pointCheckpoint stateSafe recovery behaviour
Before the data writeOld cursor remains.Retry reads the same source interval.
During/after a write with uncertain acknowledgementCursor should still be old until success is confirmed.Retry may read the interval again; the same key/version must not be duplicated.
After write succeeds, before control updateData may be present while cursor remains old.Retry re-reads; idempotent sink makes the repeated version harmless.
After checkpoint updateCursor represents the committed interval.Next run starts after the stored position.

HealthGrid uses a related pattern with ADF rather than a composite numeric key cursor. ADF captures one UTC run-start upper bound, reads a half-open source interval from the previous watermark minus a five-minute lookback to that upper bound, then advances the watermark only after Bronze-to-Silver succeeds. The same upper bound is reused for extraction and checkpointing; the checkpoint update is monotonic and row-count-checked. An explicit NO_DATA result skips both the Silver write and checkpoint advancement.

The lookback is a recovery aid, not a guarantee that every late change will be found. The version-aware merge must absorb the overlap, and the source contract must ensure that updated_at actually changes when a row changes.

Protect the checkpoint from overlapping runs

Moving the checkpoint after the write is necessary, but concurrent runs create another problem. Suppose run A starts first and captures an older upper bound. Run B starts later, captures a newer upper bound, finishes quickly and stores it. If run A finishes afterwards and blindly writes its older checkpoint, progress moves backwards.

HealthGrid protects its checkpoint with a monotonic update and verifies that exactly one control row was changed. The Uber Eats SQL path documents a stronger transactional compare-and-swap checkpoint update: the update expects the control row to still contain the value read by the run, and rolls back if the row is stale or non-unique. Pipeline concurrency is also configured to limit competing writes for that source.

The conceptual compare-and-swap contract is:

UPDATE dbo.pipeline_control
SET last_successful_watermark = @new_watermark,
    last_run_id = @run_id
WHERE control_id = @control_id
  AND last_successful_watermark = @watermark_read_at_start;

-- The transaction must verify that exactly one row was updated.
-- Zero rows means another run changed the cursor or the row is missing.
-- More than one row means control metadata is not unique.
-- Either case should roll back and require reconciliation.

The important part is not this exact SQL dialect. It is the compare-and-swap invariant: a run may advance only the checkpoint state it actually read. A unique control row, explicit run ID, monotonicity and transaction boundary make concurrent progress changes observable.

Treat files as versioned deliveries

Not every source is a database table. HealthGrid's ADLS CSV branch uses a per-file manifest rather than applying a row timestamp watermark to the file itself. The manifest records file identity using path, name, last-modified time, size and, where available, content MD5. A file moves through IN_PROGRESS, COPIED, PROCESSED or FAILED; finalization occurs only after Bronze-to-Silver succeeds.

This is a good example of matching the cursor to the source contract. The file modification time is a delivery property; a reported_at timestamp inside the file is a business event time. They answer different questions. A file manifest can skip the same processed file version, but it does not automatically deduplicate rows when a producer replaces a whole snapshot with a new file version that overlaps earlier records.

The Delta write and Azure SQL manifest update are not one atomic distributed transaction. If Delta processing succeeds but manifest finalization fails, the file remains in an intermediate state that requires reconciliation rather than blind automatic replay. That is an explicit recovery choice: safer than silently appending the same file again, but it introduces an operational procedure.

Test replay as a state transition

A meaningful replay test compares target state before and after repeated execution. It should not stop at checking that the job returned a success status.

ScenarioExpected invariant
Same source interval submitted twiceNo duplicate key/version in a history target; current-state values remain unchanged.
Two rows share the same timestampComposite cursor includes both in deterministic key order.
Null key or null cursor timestampBatch fails before checkpoint advancement.
Older version arrives after newer versionCurrent-state target does not move backwards.
Same key/version has a different business payloadFail or route to reconciliation; do not choose an arbitrary winner.
Failure after write but before checkpoint updateRetry converges to the same target state.
Two runs attempt to advance the same checkpointOnly the run with the expected control state may advance it.
Hard delete or update later than lookbackExplicit CDC, tombstone, reconciliation or documented limitation is applied.

For NovaCart, the code also checks invalid cursor rows before filtering, and stores run metadata in a per-table ingestion-control record. In Uber Eats, checkpoint concurrency and SQL source boundaries are documented alongside tests for replay and repository-owned Silver processing. These are different implementations of the same idea: the run must leave enough evidence to decide whether a retry is safe.

What replay safety does not solve

  • Hard deletes: a timestamp cursor over existing rows cannot discover a row that has disappeared. Use log-based CDC, soft-delete flags or snapshot reconciliation.
  • Arbitrarily late changes: no finite lookback guarantees capture of records backdated beyond the overlap. Establish a source SLA, use CDC or reconcile periodically.
  • Broken source timestamps: if a source mutation does not update its version column, the cursor can miss it.
  • Schema drift: idempotent writes do not make incompatible source and target schemas compatible. Schema changes need validation and controlled migration.
  • Cross-system atomicity: a data-table transaction and a control-table transaction are often separate. Design for the uncertain gap and retain run-level evidence.
  • Duplicate business meaning: a repeated delivery can be harmless at key/version grain while two genuinely different business events still require separate event identifiers and history semantics.

HealthGrid and Uber Eats were also successfully run in their intended Azure environments, with infrastructure later decommissioned. The examples use synthetic portfolio data and do not imply a continuously hosted production service or universal exactly-once guarantee.
