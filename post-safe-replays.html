Making incremental loads safe to replay

7 November 2026·2 min read
  • data-engineering
  • incremental-loading
  • azure

Every incremental pipeline fails eventually. A cluster drops, a file arrives twice, a run is cancelled halfway. What matters is what happens when you run it again. In my projects I treat "safe to rerun" as a design requirement and not something to hope for. Three habits do most of the work.

1. Move the watermark only after the write succeeds

The Uber Eats project has a written checkpoint contract that separates two events that are easy to blur: extracting rows and committing progress. If the checkpoint moves when the extract finishes, a failure during the load loses data silently, because the next run starts after rows that never landed. If it moves only once the write is confirmed, the worst case is that the next run reads some rows again. The next two habits make that harmless.

2. Merge on a key, and guard it with a version

HealthGrid loads with a merge and not an append. The merge rejects null or duplicate keys, and it updates an existing row only when the incoming source version is newer. If the same version arrives with different content, the run fails instead of overwriting. Replaying a batch therefore either changes nothing or stops and says why. A quiet overwrite is the failure I least want.

3. Pair the timestamp with a tiebreaker

Timestamps are not unique: several rows can share one. In NovaCart each source has a watermark made of a timestamp and a primary key, stored in a control table. A run can resume from an exact position and not from a time that may split a group of rows. A Delta MERGE then keeps the current-state tables correct if a window is read twice.

What this does not give me

Timestamp watermarks depend on the source updating its timestamp reliably. They are not change data capture, and they do not see deletes unless the source marks them. The HealthGrid README says so, and the Uber Eats incremental contract lists deletes and late changes as cases to handle explicitly. The NovaCart notebooks are saved without cell outputs, so the repository holds the logic and not a record of it running. I would still like to add a test that runs one batch twice and asserts the target is identical.
