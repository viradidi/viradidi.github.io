Why Silver stays append-only while Gold rebuilds state

12 November 2026·2 min read
  • streaming
  • cdc
  • iceberg

AtlasFlow keeps two different ideas of "the data" apart: what happened, and what is true now. Silver holds the first and Gold holds the second, and that split drives most of the design.

Silver is a log, so it only appends

Debezium turns every committed PostgreSQL change into an event. Bronze keeps the raw envelope, untouched. Silver parses those events into one normalised change history with the entity identifier, the source table, the operation type and a data-quality label. It never updates a row. A change that arrives later is another row, and the order of changes stays visible.

That matters for three reasons. Nothing is lost if a Gold rule turns out to be wrong. I can reprocess from Silver without going back to the source. And I can explain exactly why a shipment looks the way it does.

Gold rebuilds the current state

Operations users do not want a change log. They want one row per shipment. The Gold Flink SQL job rebuilds the latest valid record of each entity from Silver using temporary views inside the streaming query. It joins them into the shipment model, classifies risk and upserts by shipment_id. A late update changes that shipment's row. It does not add a new one.

What this costs

I did not create a current-state table per entity in Silver, so the reconstruction logic sits in Gold. That makes entity selection, update ordering and recovery after a restart the things most worth testing. Gold is also not an event ledger. If I need what happened and when, I read Silver.

What it does not show

The platform runs locally in Docker Compose on synthetic data. I make no claims about throughput or latency, and a managed deployment would need partitioning, ordering and recovery revisited. The design shows a clean separation of concerns. It does not show scale.
