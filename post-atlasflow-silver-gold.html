Why Silver stays append-only while Gold rebuilds state

12 November 2026·8 min read·Updated 22 November 2026
  • streaming
  • cdc
  • flink
  • iceberg

In a change-data-capture pipeline, there are two different questions hiding inside the phrase current data: what changes did the source emit, and what is the latest valid state of each business entity? Keeping those questions separate makes replay, investigation and downstream modelling easier. In AtlasFlow, Silver records the sequence of changes; Gold turns that sequence into a shipment-level operational view.

This is not just a naming convention for medallion layers. It determines what gets retained, which layer owns state reconstruction, and what has to be true about event ordering before a “latest row” query is safe.

The pipeline and its contracts

AtlasFlow is a local logistics control-tower demonstration built around synthetic operational data. PostgreSQL is the write path for seven related entities: customers, orders, inventory balances, carriers, shipments, tracking events and disruptions. Debezium reads committed database changes through PostgreSQL logical replication and publishes them to Kafka. The business CDC stream is consolidated into atlasflow.cdc.v1.

The project separates responsibilities across three persistent Iceberg datasets:

LayerPersistent tableWhat it represents
Bronzeatlasflow.bronze.cdc_eventsThe raw Debezium event envelope plus Kafka topic, partition, offset and ingestion metadata.
Silveratlasflow.silver.cdc_changesA normalized, append-only record of source changes, including entity identity, operation, event time and quality status.
Goldatlasflow.gold.shipment_control_towerA current-state serving model with one record per shipment and explainable risk attributes.

Trino queries the Iceberg tables and Superset provides the dashboard layer. The Flink jobs are long-running streaming jobs, not a scheduled batch that simply truncates and reloads every layer.

Why Silver is append-only

A Debezium event describes a source mutation. Its operation indicates whether the record was created, read as part of a snapshot, updated or deleted. The Silver transformation parses the envelope into a common change record: source table, operation, entity identifier, event time, normalized attributes, quality classification and lineage metadata.

Silver does not overwrite the previous representation of the entity. If shipment SH-1042 moves from IN_TRANSIT to DELAYED, both changes remain available as separate events. That gives downstream engineering three important capabilities:

  • Reconstruction: a corrected Gold transformation can be evaluated against retained change history, rather than depending on the source system still having the old event.
  • Explanation: an analyst can inspect the sequence of changes that led to the current shipment status.
  • Decoupling: ingestion does not need to predict every future analytical view. New consumers can derive different state models from the same normalized history.

Append-only does not mean “keep every malformed payload and pretend it is valid”. The Silver contract also classifies event quality. Gold filters to valid records before state selection; invalid records should remain inspectable through their quality and raw-payload fields instead of quietly influencing the business view.

How Gold reconstructs state

Operations users generally do not want a stream of every customer or carrier update. They want a compact answer to questions such as “which shipments need attention right now?” AtlasFlow therefore reconstructs the latest valid record for each source entity in the Gold Flink SQL job.

The essential shape of the query is a windowed rank over each source entity:

CREATE TEMPORARY VIEW latest_versions AS
SELECT *,
       ROW_NUMBER() OVER (
           PARTITION BY source_table, entity_id
           ORDER BY event_time DESC
       ) AS row_rank
FROM cdc_stream
WHERE quality_status = 'VALID'
  AND entity_id IS NOT NULL;

CREATE TEMPORARY VIEW current_rows AS
SELECT *
FROM latest_versions
WHERE row_rank = 1
  AND operation <> 'd';

The partition key is a pair, not just an entity ID. Customer 42 and shipment 42 are different source records, so the source table is part of the identity. The query first ranks valid events and then removes a latest delete operation from the current-state view. That distinction matters: filtering deletes before ranking could resurrect an older version of a row that was subsequently deleted.

Temporary views then project the latest current rows for customers, orders, shipments, carriers and inventory. Inventory is aggregated into available-to-promise quantity. Tracking events are separately ranked per shipment. Active disruptions are summarized by shipment. The resulting models are joined at shipment grain and written to the keyed Gold sink.

The Gold table is intentionally not an event ledger. It stores the latest operational view: shipment and order context, customer and carrier, inventory availability, latest tracking details, active disruption count, a deterministic risk level and a primary reason. A shipment is high risk when explicit conditions such as delayed status, a critical tracking exception, active disruption or insufficient inventory apply. This is explainable rule-based classification, not a predictive score.

Ordering, deletes and event time

“Latest” is only meaningful when the ordering rule is correct. The current Gold query orders each entity by event_time DESC. That is useful, but it creates an important edge case: two events for the same entity can share the same event timestamp. SQL window functions do not promise a stable winner when all ordering expressions tie.

The project already carries Kafka partition and offset metadata into the normalized change record. A production-hardening step would define an authoritative source version and a deterministic tie-breaker for every entity. A possible order is:

ORDER BY source_event_time DESC,
         source_log_position DESC,
         kafka_partition DESC,
         kafka_offset DESC

The source log position is the key part: it should represent the source’s actual change order. Kafka offset is only a safe tie-breaker for records whose key is consistently routed to the same partition. If a key can move between partitions, offsets from different partitions are not globally comparable. The tracking-event model already uses event time followed by partition and offset to choose the latest event within its shipment partition; the general entity-state model deserves the same explicit ordering contract.

Deletes need equal care. A delete is not simply an event to discard. It is a versioned fact that says the entity must no longer appear in the current-state view. Keeping that delete event in Silver makes it possible for Gold to suppress the entity. If a later valid create or update is permitted by the source’s key lifecycle, it must be ordered after the delete according to the same authoritative version rule.

Checkpoints and recovery

The Flink SQL templates configure a 10-second checkpoint interval, EXACTLY_ONCE checkpointing mode, a 60-second timeout, a tolerance of three failed checkpoints, and checkpoint/savepoint directories. The Iceberg Silver source is configured for streaming reads using TABLE_SCAN_THEN_INCREMENTAL: first scan the existing table, then discover new append-only snapshots. This is an important boundary: the Iceberg streaming reader is not a row-level CDC feed for arbitrary updates and deletes. AtlasFlow makes this workable because the Silver contract writes each normalized source change as a new append-only event row.

There is a subtle but important boundary here. Flink checkpoint mode describes how Flink snapshots and restores the state and positions managed by the job. It does not, by itself, prove an end-to-end exactly-once business effect across PostgreSQL, Kafka, Flink, Iceberg, the catalog and object storage. That claim depends on connector commit semantics, stable checkpoint storage, recovery behaviour and the external systems participating correctly.

The Gold source definition sets its watermark to event_time - INTERVAL '99' YEAR. Its accompanying comment explains the reason: historical Silver rows must participate in state rebuilding during the initial Iceberg table scan. The watermark therefore lags event time by an extremely long interval, postponing event-time-driven state cleanup. This is an implementation-specific choice with a cost: state can accumulate as the history grows. It should be measured and revisited before using the pattern on a large, continuously growing history.

Trade-offs and hardening priorities

ChoiceBenefitCost or follow-up
Append-only Silver CDC historyRetains what changed and supports reprocessing.History grows; retention, compaction and schema evolution need operational policy.
Reconstruct state in GoldAvoids maintaining a persistent current-state table for every source entity in Silver.Gold owns complex joins, version ordering, delete handling and restart correctness.
One row per shipment in GoldSimple operational serving grain for dashboards and attention queues.Not suitable for event-by-event audit questions; use Silver for history.
Very long event-time watermark delayAllows older historical events to participate in the state-building query.Can retain large state; requires measurement, checkpoint planning and an explicit cleanup strategy.
Rule-based risk classificationReasons are deterministic and explainable to operations users.Rules need business ownership and do not estimate probability of late delivery.

For the current implementation, the most valuable next tests are not generic “pipeline succeeded” checks. They are state invariants:

  1. Insert, update and delete the same source entity and assert that only the correct latest non-deleted version appears in the current view.
  2. Send two same-key events with equal event timestamps but different source positions and assert that the authoritative later change wins.
  3. Restart the Gold job from a checkpoint while new CDC events arrive and reconcile the keyed sink against a bounded replay.
  4. Rebuild the shipment view from a known Silver snapshot and compare row counts, join cardinality and risk reasons with the streaming output.
  5. Measure retained state and checkpoint size as Silver history grows; do not infer scale from a local synthetic run.

When to use this pattern

Keep an append-only normalized change history when auditability, replay and multiple downstream interpretations matter. Build current-state tables separately when consumers need a stable business grain. The pattern is especially useful when source changes arrive continuously but dashboards need a coherent “now” view.

It is not free. It moves correctness questions into the state reconstruction layer: key identity, source ordering, delete semantics, state retention, checkpoint recovery and reconciliation. Those are explicit engineering contracts, not details a medallion diagram can solve on its own.

Implementation scope

AtlasFlow is a successfully executed local Docker Compose engineering demonstration using synthetic logistics data. Its repository documents PostgreSQL → Debezium → Kafka → Flink → Iceberg → Trino/Superset. It is not a continuously hosted production service, and this article makes no throughput, latency or availability claims.
