AtlasFlow: Real-Time Logistics Control Tower

A real-time logistics data platform that turns PostgreSQL changes into a continuously updated, shipment-level control tower using Debezium, Kafka, Flink SQL, Apache Iceberg and Trino.

Business problem and objectives

Logistics operations span order management, warehouse and inventory systems, transportation and carrier management, shipment tracking and disruption monitoring. When these systems run independently, operations teams cannot see shipment status in one place or spot problems early. A unified control tower helps identify delayed shipments, inventory shortages, active disruptions and shipments that need attention as the source data changes.

Change data capture and stream processing keep that view current without each application pushing data to a dashboard. The operational database stays the source of truth, and the view follows its changes.

The Gold table is designed to answer the questions an operations team asks:

  • Which shipments are high-risk?
  • Which carriers have the most delayed or high-risk shipments?
  • Which warehouse regions have inventory shortages?
  • Which shipments are affected by active disruptions?
  • Why was a particular shipment classified as high-risk?

The documented Superset dashboard shows total, high-risk and inventory-shortage shipments, active disruption links, shipments by risk level, high-risk shipments by carrier, shortages by warehouse region, and an attention queue with the primary risk reason. No financial, latency or throughput results are claimed.

Objectives

  • Unify order, customer, carrier, inventory, shipment, tracking and disruption data in one current-state view.
  • Keep that view current as source rows change, without each application pushing data to a dashboard.
  • Explain why each shipment is classified as high-risk, medium, watch or low.

System architecture

The pipeline follows a Bronze, Silver and Gold design. The diagram below is rendered from the Mermaid source in the project README.

Technology stack

  • Source systems PostgreSQL, Python (synthetic data generator)
  • CDC and streaming Debezium, Apache Kafka, Apache Flink SQL
  • Lakehouse storage Apache Iceberg, Iceberg REST Catalog, RustFS (S3-compatible)
  • Query and BI Trino, Apache Superset
  • Infrastructure Docker Compose
  • Observability Prometheus, Grafana, Kafka UI, Flink Dashboard
  • Development and automation GitHub Actions static validation, PowerShell scripts, Python

How the platform works

Stages

  1. 1. PostgreSQL source: the atlasflow_ops database with seven related tables: customers, orders, inventory balances, carriers, shipments, tracking events and disruptions. The generator writes here first.
  2. 2. Debezium CDC: captures committed changes through PostgreSQL logical replication, with an initial snapshot followed by ongoing changes.
  3. 3. Kafka: routes business changes to one consolidated topic, atlasflow.cdc.v1.
  4. 4. Flink Bronze: a streaming job ingests the raw Debezium envelopes and Kafka metadata (topic, partition, offset) into Iceberg.
  5. 5. Flink Silver: parses and normalises events into one append-only change history, with entity identifiers, source table, operation type and data-quality labels.
  6. 6. Flink Gold: a long-running Flink SQL transformation rebuilds the latest record of each entity from Silver, joins them, classifies risk and upserts by shipment_id.
  7. 7. Iceberg storage: three tables, bronze.cdc_events, silver.cdc_changes and gold.shipment_control_tower, registered in an Iceberg REST Catalog on RustFS S3-compatible object storage.
  8. 8. Trino: SQL access to the Iceberg tables, including the Gold serving table.
  9. 9. Superset: the business-intelligence layer, connected through Trino.
  10. 10. Observability: Prometheus and Grafana, with Kafka UI and the Flink Dashboard for inspection.

Layers

  • Bronze keeps the raw CDC events exactly as captured.
  • Silver keeps normalised, append-only change history in a common structure.
  • Gold holds one current-state record per shipment: shipment, order, customer and carrier details, warehouse region, product and quantity, available-to-promise inventory, latest tracking event and delay, active disruption count and expected delay, an inventory-shortage flag, a risk level and a primary risk reason.
  • Risk classification is rule-based, in priority order. HIGH: the shipment is delayed or exceptional, tracking reports a critical exception, an active disruption exists, or available inventory is below the order quantity. LOW: delivered, with no higher-priority condition. MEDIUM: the latest tracking event reports a delay. WATCH: no higher-priority signal.

Engineering decisions

  • CDC, not direct application-to-dashboard movement. The generator commits to PostgreSQL first and Debezium captures the committed changes from the database log. The cost is a dependency on PostgreSQL availability, replication configuration and connector health.
  • One consolidated CDC topic. One event ingress for the pipeline. Consumers must read the source-entity metadata correctly, and partitioning should be revisited as volume grows.
  • Append-only Silver history. Silver keeps normalised changes and does not maintain a current-state table for every entity. More reconstruction logic therefore sits in Gold, which makes testing entity selection, update ordering and recovery important.
  • Streaming Gold reconstruction. Gold builds temporary views inside its streaming query to find the latest valid record of each entity, then combines them into the shipment model.
  • Shipment-keyed upserts. Gold is keyed by shipment_id, so a shipment row updates as new changes arrive. It is not an event ledger. Event-by-event history stays in Silver.
  • Explainable, rule-based risk. Explicit conditions produce a risk level and a primary reason that operations users can read. The classification is deterministic and not predictive, and thresholds need business review.
  • Raw, normalised and business-ready data kept apart. Bronze, Silver and Gold each have one job.
  • Local containerised infrastructure. The whole stack starts with Docker Compose as a self-contained environment.

Reliability, testing and data quality

Repository validation. A GitHub Actions workflow runs static checks of the repository structure, SQL template presence, Python syntax, YAML and JSON configuration, and key pipeline contracts. It does not start the Docker stack, run the Flink jobs or verify CDC propagation.

Live execution. The completed platform was run end to end in its intended local environment. For a running stack the repository provides smoke-test and verification scripts and a Trino query pack. Silver also labels data quality on each normalised change.

Deployment and operations

The platform runs on Windows with Docker Desktop (Compose v2), PowerShell and Python 3.10 or later. A preparation script sets up the local environment, and docker compose up -d --build starts the platform. A manual runbook documents the eight-step pipeline procedure, the Superset connection and the dashboard. The generator has a baseline scenario, a fault-bundle scenario (a delayed shipment, a tracking exception and an active port disruption) and an optional continuous baseline mode. Prometheus, Grafana, Kafka UI, the Flink Dashboard and Docker health checks cover monitoring.

Results and implementation evidence

Implemented

  • Runs end to end in its intended local environment: PostgreSQL, Debezium, Kafka, three Flink streaming jobs, Iceberg tables, Trino and Superset on Docker Compose.
  • Gold holds one current-state record per shipment, written by keyed upserts on shipment_id.
  • Smoke-test and verification scripts and a Trino query pack are provided for a running stack.

Boundaries

  • This is a local educational and demonstration environment. It does not establish production high availability, disaster recovery, cloud scalability or production security.
  • The data is synthetic, generated for a fictional operator. Results illustrate pipeline behaviour and business logic and are not measurements from a real logistics operation.
  • The risk classification is rule-based and does not predict late delivery.
  • No throughput, latency, availability or cost figures are claimed.
  • A portable Superset dashboard export is not included in the repository.
  • Topic partitioning, throughput and ordering would be revisited for a managed production platform.
