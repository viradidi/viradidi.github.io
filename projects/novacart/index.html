NovaCart Incremental Retail Lakehouse

An incremental retail lakehouse on Azure Databricks that moves products, orders and payments from Azure SQL through Bronze, Silver and Gold Delta tables, with watermarks, MERGE and SCD Type 2 history.

Business problem and objectives

Retail operations produce related product, order and payment data. Reporting needs a consolidated view of orders and payments, category-level revenue and payment performance, and both current and historical order analysis, without rebuilding every downstream dataset on each run.

Objectives

  • Load only changed rows from Azure SQL at every layer.
  • Keep both current state and order history for analysis.
  • Refresh only the Gold datasets affected by a change.

System architecture

Databricks reads the Azure SQL tables through Lakehouse Federation. Bronze records progress in an ingestion control table. Silver cleans, standardises, deduplicates and merges. Gold identifies changed entities and updates curated datasets. A Databricks Job runs the notebooks in order, followed by a dashboard task and a SQL alert.

How the platform works

  1. Bronze: source-specific timestamp and primary-key tracking, with a control table recording progress and row-write metadata.
  2. Silver: cleaning, standardisation, deduplication, quality handling and incremental Delta MERGE.
  3. Gold: orders_information (current state), orders_information_scd2 (history), category_performance, and Parquet snapshots in a Databricks Volume.
  4. Orchestration: bronze_work, silver_work, gold_work, the dashboard and the alert, linked with ALL_SUCCESS dependencies and one concurrent run at a time.

Engineering decisions

  • Watermarks reduce unnecessary reads. Their correctness depends on timestamp quality, ties, late updates and when checkpoints advance.
  • Delta MERGE keeps current-state tables correct when source rows change, given stable keys and deterministic transformations.
  • SCD Type 2 keeps order history, at the cost of more storage and transformation complexity.
  • Gold refreshes only the categories affected by a change. Reconciling against a full recomputation is the validation method.

Reliability, testing and data quality

Quality handling is part of the Silver step. A validation plan lists acceptance criteria and test scenarios. A GitHub Actions workflow packages the release and validates notebook JSON, configuration, the diagrams and README links, which is repository validation. The transformation logic itself was verified by running the pipeline end to end in Azure Databricks.

Deployment and operations

I deployed this project and ran it end to end in Azure Databricks. The Azure resources were decommissioned afterwards to control cost, which does not change the implementation or its completed run. The repository keeps the notebooks, SQL scripts, a saved job template, a dashboard export and a deployment guide for recreating the environment, plus an operations runbook, a data dictionary, an engineering-decisions document and an artifact audit.
