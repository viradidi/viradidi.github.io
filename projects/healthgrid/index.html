HealthGrid Data Platform

A metadata-driven Azure data platform that integrates synthetic hospital operational data and partner feeds into analytics-ready Gold datasets, with control tables, watermarks, a per-file manifest and audit logging.

Business problem and objectives

Healthcare networks bring together information from internal hospital systems and external partners. The sources differ in structure, delivery format and update frequency. Without reusable ingestion patterns and operational controls, the pipelines become hard to maintain, monitor and extend.

HealthGrid addresses this with configurable source ingestion, centralised control metadata, auditable pipeline execution, layered transformations and business-oriented Gold datasets.

Objectives

  • Ingest relational operational data and partner files through reusable, metadata-configured patterns.
  • Protect existing rows from stale or conflicting updates, and avoid copying a file version twice.
  • Make every run auditable from source to Gold.

System architecture

A master Azure Data Factory pipeline calls child pipelines for source-to-Silver ingestion, Silver-to-Gold processing and status notification. An Azure SQL control database holds the source configuration, load strategies, watermarks and audit records. Azure Data Lake Storage Gen2 receives the source extracts and partner files, and Azure Databricks processes them through Bronze, Silver and Gold.

The diagram shows the whole platform: five numbered areas for sources, ingestion and orchestration, storage, processing and consumption, with metadata, security and infrastructure areas beneath them.

How the platform works

  1. Sources. PostgreSQL hospital operational data (hospitals, doctors, patients) and partner CSV feeds (laboratory results, insurance providers).
  2. Metadata and orchestration. ctrl.table_config selects the active sources and their load strategy. Data Factory reads it and runs the source-to-Silver and Silver-to-Gold pipelines.
  3. Landing and Bronze. Extracts land in ADLS Gen2 in timestamped batches. A Databricks notebook adds landing and ingestion timestamps and appends each batch to its Bronze table.
  4. Silver. The Bronze-to-Silver notebook processes the current batch with the configured FULL, APPEND or MERGE strategy. A calendar dimension supports date-based reporting.
  5. Gold. Three Databricks SQL notebooks build patient_360, hospital_daily_summary and lab_test_trends. The Gold pipeline reads the active SILVER_TO_GOLD metadata records and resolves each notebook path from gold_table_name.

Engineering decisions

  • Behaviour lives in metadata. Active sources, load type, watermark column, merge keys and paths are configuration, so ingestion is configured and not hard-coded. Gold transformation SQL stays in the individual notebooks.
  • A version guard on MERGE. The merge rejects null or duplicate business keys and updates a row only when the incoming source version is newer. An equal-version conflict fails and does not overwrite.
  • Watermarks for PostgreSQL, a manifest for CSV. PostgreSQL uses timestamp watermarks in ctrl.watermark. CSV files use ctrl.file_ingestion_manifest, which identifies each file version and tracks it through copy and Bronze-to-Silver. A file version is finalised only after Bronze-to-Silver succeeds.
  • Gold waits for both branches. The master pipeline starts Silver-to-Gold only when both source branches have succeeded. The notification branch runs after Gold completes, so it reports either outcome.
  • Idempotent audit records. The audit log records the Data Factory run ID, stage, status, row count and timestamps, with uniqueness per parent run, table and stage and idempotent retry upserts.
  • An honest watermark boundary. The PostgreSQL watermark is not change data capture. Its correctness depends on reliable source timestamps and on suitable watermark semantics.

Reliability, testing and data quality

Controls. Per-file CSV states (IN_PROGRESS, COPIED, PROCESSED, FAILED) block automatic recopy of a file version left unresolved by a prior run. Success and failure updates wrap each notebook run, and a notification pipeline assembles run status for a Logic Apps endpoint.

Repository validation. A GitHub Actions workflow checks the exported JSON, Databricks notebook code-cell syntax, Python syntax, required documentation, the preserved architecture-image embed and selected credential patterns. These are static checks. They do not execute Data Factory pipelines or Databricks workloads. The platform itself was run end to end in Azure, which is separate validation.

A validation plan documents repeatable tests, measurable acceptance criteria and release gates.

Deployment and operations

A redeployment follows a documented sequence: provision the PostgreSQL source, Azure SQL control database, ADLS Gen2, Databricks workspace and Data Factory; configure linked services and credentials through secure configuration and Key Vault; create the source tables and load the synthetic data; create and seed the control metadata; configure paths, catalog, schemas and notebook references; publish the Data Factory assets; run the master pipeline; and reconcile record counts across source, Bronze, Silver and Gold.

The source-table creation script contains DROP TABLE statements and is meant for controlled initial setup or reset in a disposable environment. The Azure environment was decommissioned after the run to control cost. The repository keeps the scripts, exports, notebooks, sample data, mapping workbook and diagram.

Results and implementation evidence

Implemented

  • Run end to end in its original Azure environment.
  • Five configured sources: hospitals and doctors (FULL), patients (MERGE), lab_results (APPEND) and insurance_providers (FULL).
  • Three Gold datasets: patient_360, hospital_daily_summary and lab_test_trends.
  • Seven engineering and operations documents, a source-to-target mapping workbook and exported Data Factory and Databricks artifacts.

Boundaries

  • Some exported Azure and Databricks artifacts carry older resource, catalog or workspace identifiers. They are deployment references and not a different project, and a new deployment should update them together.
  • The data is synthetic and the project is educational. It is not a clinical system and processes no real patient records.
  • Timestamp watermarks rely on source update semantics and need review for late-arriving changes, deletes and timestamp collisions. MERGE depends on correctly configured business keys and sensible source deduplication.
  • Environment-specific catalog, workspace, notebook, storage and integration references must be updated when redeploying.
