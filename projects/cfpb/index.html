CFPB Consumer Complaint Analytics

A completed end-to-end Microsoft Fabric implementation that takes 903,983 historical CFPB consumer complaint records from a raw CSV to a Power BI report, with documented data-quality decisions, pipeline orchestration and DEV-to-PROD deployment.

Business problem and objectives

Consumer complaints show which financial products, issues and company responses consumers report. This project uses a historical complaint dataset (903,983 records, 18 columns) to explore how complaint volumes change over time, which products, issues and companies account for the most complaints, how consumers submit complaints, how often companies respond on time, and how dispute rates vary by response outcome.

It also records the reasoning behind each data-cleaning decision: when to standardise a value, when to preserve missing information and when to quarantine a record.

Objectives

  • Take a raw complaint CSV through Bronze, Silver and Gold to a dimensional reporting model.
  • Standardise categories without inventing information: keep, standardise or quarantine, and never guess.
  • Deliver a Power BI report and promote the solution from DEV to PROD with deployment pipelines.

System architecture

A Fabric ingestion pipeline downloads the source through the Kaggle API into a Lakehouse as raw CSV (Bronze). A PySpark notebook profiles, validates and cleans it into a Silver table, and routes invalid records to quarantine. A SQL stored procedure loads Gold fact and dimension tables in a Fabric Warehouse. A semantic model with DAX measures feeds a Power BI report. A separate end-to-end pipeline orchestrates ingestion, Silver processing and Gold loading, and Fabric deployment pipelines promote the solution from DEV to PROD.

How the platform works

  1. Ingestion. The pipeline downloads the source archive through the Kaggle API and extracts the CSV into the Lakehouse.
  2. Bronze. The raw file is preserved for traceability and reprocessing. CSV parsing handles the header row, quoted fields with commas, line breaks inside quoted fields and escaped quotation marks.
  3. Silver profiling and validation. The notebook examines row and column counts, column types, complaint ID uniqueness, missing values, category variations, and date and ZIP-code patterns.
  4. Silver cleaning. Dates are converted and invalid records are quarantined. Products and sub-products are standardised from the CFPB April 2017 category changes, and issues and sub-issues use project-defined mappings. Company names and ZIP codes are cleaned, and original values are kept beside the standardised columns.
  5. Gold. A dimensional model in Fabric Warehouse has a complaint fact table and dimensions for dates, products, issues, companies and other attributes, joined by surrogate keys and loaded by gold.sp_load_gold.
  6. Semantic model and report. The model connects the Gold tables and defines Total Complaints, Timely Response %, Consumer Dispute %, Average Days to Send to Company and Complaints by Sent Date. The Power BI report has three pages.
  7. Orchestration. The end-to-end pipeline connects ingestion, the Bronze-to-Silver notebook and Gold loading through activity dependencies, and run history supports monitoring and troubleshooting.

Engineering decisions

  • Quarantine, never guess. Records where the date sent to the company is earlier than the date received go to a quarantine table. The project does not guess corrected dates, and quarantined records stay available for investigation.
  • Keep originals beside standardised values. Columns such as product_standardized and issue_standardized sit next to the original fields, which keeps the mappings traceable and reviewable.
  • Honest about mapping authority. Product mappings follow CFPB documentation. Issue and sub-issue mappings are project-defined reporting choices and are not presented as an official CFPB crosswalk.
  • Do not invent information. Missing values are investigated before handling. A missing consumer dispute status is not treated as "No", and missing statuses are excluded from the Consumer Dispute % denominator.
  • ZIP codes as text. The notebook recognises five-digit and masked values, applies state-and-prefix plausibility rules, sets unreliable values to null while keeping the complaint, and outputs three digits followed by XX.
  • Staged deployment. A first deployment to an empty target uses two rounds, so the Silver table that the Gold-loading procedure depends on exists before the Warehouse is deployed.

Reliability, testing and data quality

Reconciliation. Valid and quarantined counts reconcile to the source: 896,931 + 7,052 = 903,983. The notebook reports validation and reconciliation results for review.

Orchestration. Activity dependencies control execution order, and pipeline run history supports monitoring and troubleshooting.

CI/CD scope. The project demonstrates manually triggered DEV-to-PROD promotion with Fabric deployment pipelines. It does not implement a Git-triggered build, automated test and deployment workflow.

Deployment and operations

The deployment walkthrough uses two rounds. Round 1 deploys the Lakehouse, ingestion pipeline and Bronze-to-Silver notebook. It then verifies that the connections and notebook Lakehouse bindings target the intended environment, runs the pipeline and the notebook, and confirms that silver.consumer_complaints is visible through the target Lakehouse SQL analytics endpoint. Round 2 deploys the Warehouse, end-to-end pipeline, semantic model and Power BI report, verifies the bindings, runs the pipeline to populate Gold and checks report access to the target data.

To reproduce the project, obtain the source dataset, create the Fabric workspace and Lakehouse, configure the ingestion connection, run ingestion and the notebook, create the Gold objects and loading procedure, run the end-to-end pipeline, configure the semantic model and report, and follow the staged deployment. Workspace references, item identifiers, connection settings and source paths must be updated for your own environment.

Results and implementation evidence

Implemented

  • Source snapshot of 903,983 records with 18 columns; 896,931 cleaned Silver records and 7,052 quarantined records, which reconcile to the source (896,931 + 7,052 = 903,983).
  • A Gold dimensional model in Fabric Warehouse loaded by the gold.sp_load_gold stored procedure.
  • A semantic model with five DAX measures and a three-page Power BI report: complaint overview, complaint drivers, and response and resolution.
  • A documented two-round DEV-to-PROD deployment using Fabric deployment pipelines.

Possible future improvements
