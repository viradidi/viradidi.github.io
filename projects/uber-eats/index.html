Uber Eats Data Analytics Platform

A metadata-driven Azure data platform that ingests restaurant-delivery data from a REST API, CSV files and an incremental SQL source, with written controls for incremental correctness, checkpoint safety, reconciliation and recovery.

Business problem and objectives

A delivery platform needs a consistent way to ingest and process data that comes from different systems: payments, deliveries, order statuses, ratings, drivers, promotions and delivery zones. Each system has a different shape and a different way of changing.

The engineering challenges are to ingest REST API endpoints and CSV files, extract incrementally from a SQL source, coordinate ingestion through reusable pipelines, organise the data in cloud storage, keep configuration and metadata apart from pipeline logic, and make the whole workflow understandable and reproducible.

Objectives

  • Ingest REST API, CSV and SQL sources through reusable, metadata-configured pipelines.
  • Make extraction boundaries, watermark meaning, late changes and replay assumptions explicit.
  • Provide reconciliation queries and a recovery runbook, so a failed run can be investigated and rerun safely.

System architecture

Three source patterns each have their own Azure Data Factory pipeline: an API initial load, a CSV initial load and a SQL incremental load. Metadata and control configuration sit apart from the pipeline logic, and Azure Key Vault holds the secrets configuration. Data lands in ADLS Gen2 and Databricks notebooks process it. Metadata, control state and secret management are supporting concerns and not business-data layers.

How the platform works

  1. Sources. A FastAPI mock REST API serving payments, deliveries, ratings and order status; CSV files for drivers, promotions and zones; and a relational SQL source.
  2. Ingestion pipelines. Separate Data Factory pipelines handle each pattern. Metadata maps CSV files to destination folders, and the SQL pipeline follows an incremental pattern with watermark and checkpoint handling.
  3. Storage. ADLS Gen2 receives the ingested data.
  4. Processing. Databricks notebooks cover seven datasets: deliveries, drivers, order statuses, payments, promotions, ratings and zones. They read the Bronze location from a bronze_root widget, so they can be pointed at another environment.
  5. Silver serving boundary. The implemented serving boundary is the Silver layer, produced by the Databricks notebooks. The repository does not establish a Gold or reporting layer, so none is claimed here.
  6. Reconciliation and operations. Reconciliation audit queries, an operational-health report and data-quality-trend queries support investigation after a run.

Engineering decisions

  • Incremental correctness is written down. The incremental source contract sets out, for each table, the keys, watermarks, late-arriving changes, deletes, replay and reconciliation requirements. A SQL incremental-load review records bounded extraction behaviour and known limitations.
  • Checkpoint safety. A checkpoint concurrency contract separates a successful extraction from the conditions that must hold before progress is committed.
  • Auditability. Reconciliation SQL and quality-trend SQL give reviewers concrete queries for mismatches, rejected records and recorded failures.
  • Recovery. A runbook defines failure triage, which evidence to preserve, safe rerun decisions and acceptance checks after recovery.
  • Configuration apart from logic. Pipeline, dataset and linked-service artifacts and the metadata files are reusable. The mock API reads its key from the environment and fails closed, with no default key.

Reliability, testing and data quality

Repository tests. A standard-library unittest suite checks the CSV fixtures, API timestamp and pagination behaviour, API-key fail-closed behaviour, payment-ID generation, atomic file replacement, path resolution, README link contracts and static recovery contracts. A GitHub Actions workflow checks JSON and notebook validity, Python syntax, notebook portability, sample-data quality, API-key configuration and static recovery contracts.

Live Azure execution. None of these repository checks executes Azure Data Factory, the Spark notebooks or a deployed API. The Azure execution is separate validation, covering ingestion, processing, monitoring and recovery, which the project owner reports as complete.

Deployment and operations

The repository holds the exported Data Factory factory, pipelines, datasets, linked services and integration runtimes, plus the API source, metadata and sample data. To inspect or run it, install the Python dependencies, run python -m unittest discover -s tests -v, set an API_KEY environment variable and start the mock API with uvicorn main:app, then review the exported Azure resources before importing them. Linked services, integration runtimes, secrets, resource names and workspace paths must be set for the target environment. A recovery runbook and an operations guide cover investigating failures. Azure resources were stopped after validation to control cost.

Results and implementation evidence

Implemented

  • The project owner reports end-to-end implementation, testing, monitoring, deployment and recovery validation, and the project is marked completed.
  • A standard-library Python unittest suite and a GitHub Actions validation workflow cover the repository, and they are separate from the live Azure run.
  • Reconciliation, operational-health and data-quality-trend SQL, a recovery runbook and a project release gate are included.

Boundaries

  • The README itemises the Silver notebooks, reconciliation SQL, quality queries and recovery documents. There is no Gold or reporting layer in the implemented scope.
  • Cloud resources were decommissioned after the project ran successfully, to control cost. The repository keeps the exported pipelines, notebooks and documentation. Nothing described here is currently running.
  • The mock API's payment generator mutates a local file. It is a demonstration utility and not a concurrent production write service.
  • The data is synthetic, a deliberate design choice for a portfolio project.
  • Repository checks and cloud execution cover different scopes, and neither substitutes for the other.
