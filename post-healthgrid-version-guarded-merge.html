Why I merge on a key and guard it with a version

10 November 2026·2 min read
  • data-engineering
  • merge
  • azure

HealthGrid loads with a merge, not an append. The rule I care about most is small: a row is only updated when the incoming version is newer.

Reject bad keys first

A merge is only as good as its key. HealthGrid's merge rejects rows with null or duplicate keys before it touches the target. If two rows claim to be the same record, the run stops, and it does not pick one at random.

Compare versions, not arrival order

Data does not always arrive in the order it was created. A file can be delivered twice, or an old extract can land after a newer one. Comparing the incoming source version with the stored one means an older record cannot overwrite a newer one, whatever order the files arrive in.

Fail on a conflict

If the same version arrives with different content, the merge fails. I would rather have a failed run that someone has to look at than a quiet overwrite that nobody notices. Every stage writes to an audit log with the run ID, status and row counts, so a failure leaves a trail.

Where it stops

This protects rows that are already in the target. It does not detect changes at the source. The pipeline uses timestamp watermarks, which depend on reliable source timestamps and are not change data capture. The data is synthetic, and the project is educational and not a clinical system.
