Why I merge on a key and guard it with a version

10 November 2026·8 min read·Updated 22 November 2026
  • data-engineering
  • delta-lake
  • pyspark
  • azure

A MERGE statement is not a complete correctness strategy. It tells the table how to match source rows to target rows, but it does not automatically tell the pipeline which source version is newer, whether the source keys are unique, or what to do when two records claim to be the same version but disagree.

In HealthGrid, I treat a current-state merge as a guarded state transition: identify the business entity, prove the incoming batch is unambiguous, compare source versions, and only then let the target change. The important part is not the syntax of MERGE. It is the contract around it.

The HealthGrid loading model

HealthGrid is a metadata-driven Azure data-platform demonstration. Azure Data Factory selects source objects and load strategies from control metadata, lands source batches in ADLS Gen2, and invokes Databricks notebooks for Bronze-to-Silver processing. The target is a Delta Lake table. PostgreSQL sources include synthetic operational healthcare data; ADLS CSV feeds use a separate per-file ingestion manifest.

The metadata includes the source system and object, target paths, load strategy, optional watermark column, merge keys and active status. The same transformation notebook supports three distinct behaviours:

Load strategyBehaviourCorrectness requirement
FULLReplace the target with a complete processed snapshot.The incoming batch must represent the complete intended source state.
APPENDAdd the current batch to the target.A duplicate-delivery and file-replacement policy is required.
MERGEUpdate matching business keys and insert new keys.Stable keys, deterministic source versions and a defined conflict policy are required.

The HealthGrid sample configuration uses FULL for reference entities, MERGE for patients and APPEND for laboratory results. The article focuses on the patient-style current-state MERGE, where a newer patient record should replace an older one without allowing a delayed extract to roll the target backwards.

The business key identifies the entity

A merge key answers: which real-world entity does this source row describe? For the patient example, the configured key is patient_id. It is not the timestamp, the landing folder or the ADF run ID. Those describe a version or an execution, not the entity itself.

Before the write, HealthGrid validates that merge-key metadata exists, resolves each configured key to exactly one source column, and rejects null keys. It also groups the incoming batch by the configured key and rejects duplicates instead of choosing an arbitrary winner.

That duplicate check is essential. Suppose the same patient appears twice in one batch with two different updated_at values. If the pipeline silently takes whichever row Spark happens to return first, the output depends on execution details rather than an explicit data contract. If the source is expected to send multiple changes for a key in one batch, the pipeline must first reduce them with a documented, deterministic ordering rule. HealthGrid's merge path fails closed when duplicate business keys remain.

The version decides whether an update is allowed

The source version is the value that orders two observations of the same entity. HealthGrid passes the configured watermark/source-version column into the Silver notebook and requires it to be a DATE or TIMESTAMP. For the patient merge this is updated_at.

The core business rule can be expressed in SQL like this. This is a compact illustration of the implemented rule; the project applies it through PySpark and Delta Lake after additional validation.

MERGE INTO healthgrid.silver.patients AS target
USING patients_batch AS source
ON target.patient_id = source.patient_id
WHEN MATCHED
 AND source.updated_at > target.updated_at
THEN UPDATE SET
  target.first_name = source.first_name,
  target.last_name  = source.last_name,
  target.city       = source.city,
  target.updated_at = source.updated_at
WHEN NOT MATCHED THEN
  INSERT (patient_id, first_name, last_name, city, updated_at)
  VALUES (source.patient_id, source.first_name, source.last_name,
          source.city, source.updated_at);

Consider one patient with three observations. The example uses real fields from the HealthGrid source contract; the specific values are illustrative:

Incoming observationTarget versionExpected result
updated_at = 10:1210:05Update: incoming version is newer.
updated_at = 10:0510:12Skip: stale data must not replace newer state.
updated_at = 10:1210:12Compare payloads: identical is a replay; different content is a conflict.

Arrival time is not a reliable substitute for source version. A retry, delayed file, queue backlog or overlapping extraction can make an older source image arrive after a newer one. The source version preserves the source’s ordering semantics even when delivery order changes.

An equal-version conflict is not a tie to guess

Two rows with the same key and version can be identical because the same input was delivered again. That is a harmless replay. But they can also have different business attributes. For example, two payloads for patient_id = 481 both claim updated_at = 10:12, while one has city = Nairobi and the other has city = Kisumu.

There is no trustworthy winner in that information. The version says both payloads represent the same point in source time. Choosing one by file order or Spark partition order would hide a source-contract violation.

HealthGrid compares the business payload while excluding operational fields such as landing, insert and update timestamps. Equal version plus equal business payload is a no-op. Equal version plus different business payload fails for reconciliation. Older source versions are skipped; strictly newer versions can update.

Why fail closed?

A failed run is visible and can be investigated. A silent overwrite can make the target look healthy while concealing a contradiction in the source system. For current-state entities, preserving that distinction is more important than forcing every batch to succeed.

Validate both sides before writing

A safe source does not make an unsafe target safe. HealthGrid validates the incoming batch and the existing Delta target before applying a merge.

ValidationWhy it matters
Merge keys are configured and resolve uniquelyPrevents an empty or ambiguous match condition.
Source keys are non-null and uniqueAvoids null identity and multiple source rows competing for one target.
Source version is non-null and DATE/TIMESTAMPEnsures rows can be ordered using a real source-version value.
Source and target columns match case-insensitively, including typesPrevents an unreviewed schema drift from changing merge meaning.
Target keys are non-null and uniqueConfirms the target already satisfies the one-row-per-entity contract.
Target version is non-null and compatible with source typeMakes source-to-target version comparisons meaningful.

Schema mismatch is not treated as a harmless extra column. The notebook fails and asks for a reviewed schema migration. The target is also checked for duplicate business keys: a merge predicate cannot repair a target that already violates the intended grain.

These checks have a cost. Counting duplicates and scanning target constraints adds read work before the merge. That cost is a deliberate guardrail for a demonstration whose priority is correctness and explicit failure behaviour. At larger scale, the same invariants can be enforced with partition-aware checks, data-quality jobs, persisted uniqueness audits and carefully measured query plans, but they should not simply be removed to make a pipeline faster.

Coordinate the merge with watermark progress

The merge is only one part of an incremental load. ADF also needs to know which source interval to read next. HealthGrid captures one UTC upper bound when a table run starts and reuses that same value both in the source extraction and in the checkpoint update.

For the patient PostgreSQL path, the documented interval is:

WHERE updated_at >= :previous_watermark - INTERVAL '5 minutes'
  AND updated_at <  :captured_run_start_upper_bound

The lower bound is inclusive and includes a five-minute overlap. The upper bound is exclusive. The overlap intentionally rereads a small range to mitigate boundary timing issues; the version-aware merge makes unchanged, equal-version rows no-ops. The captured upper bound is fixed at run start, so rows updated while the copy is running are not accidentally hidden behind a later checkpoint.

Checkpoint advancement happens only after Bronze-to-Silver succeeds. If ADF reports NO_DATA, Silver skips the write and the PostgreSQL watermark does not advance. The checkpoint update is monotonic and row-count-checked: an older overlapping run should not move progress backwards.

This ordering avoids one dangerous failure sequence: source extract succeeds, watermark moves forward, then the Delta write fails. If that happened, the next run would start after rows that never made it into Silver. Advancing progress after the downstream write changes the failure mode from silent loss to possible reread, which is recoverable when the sink is replay-safe.

Failure modes and limits

A version-aware merge gives a strong current-state contract, but it does not turn a timestamp source into CDC.

  • Hard deletes: a row disappearing from the source is not visible to a timestamp query unless the source emits a tombstone or soft-delete marker. Use CDC/log-based capture or a reconciliation mechanism when deletion completeness is required.
  • Late or backdated updates: an update arriving more than the configured lookback behind the checkpoint can be missed. Five minutes is a mitigation, not a mathematical guarantee.
  • Unreliable timestamps: if writers fail to update updated_at, backdate it, or use inconsistent timezone assumptions, the version order is invalid.
  • Overlapping runs: monotonic checkpoint updates prevent backward movement, but concurrent writers still need a clear isolation and run-ownership policy.
  • Distributed atomicity: a Delta commit and an Azure SQL control-table update are not one cross-system transaction. Run IDs and commit evidence help diagnose the gap; reconciliation is still required after an uncertain failure.

HealthGrid is a successfully executed end-to-end project in its original Azure environment, but those resources were later decommissioned to control costs. The repository preserves the code and contracts; its local CI checks do not replace a fresh live Azure integration test. The records are synthetic and the project is educational, not a clinical system.
